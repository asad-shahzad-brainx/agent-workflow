The problem02

One long agent session carries too many jobs

Ideation, architecture, implementation, review, and project memory all compete for the same context window.

The executor should not need every planning tangent to change one coherent slice.

Code starts before decisions settleThe first plausible design quietly becomes the implementation.
Missing states surface lateUX and domain questions come back as code churn a week later.
Context turns into residueAbandoned branches of thought sit next to current decisions.
Self-review becomes trustThe context that wrote the code is the one declaring it finished.

Timing: 2 minutes.

Give one concrete example from your own work where implementation started before a data-model decision was stable. Keep it short and anonymized.

Land the fourth point hardest. Self-review is the failure that is hardest to notice, because the output always looks confident.

The workflow answers this by separating responsibility and moving decisions into artifacts that live outside the conversation.

The shape of it03

Three roles, one developer, and state that outlives the chat

Planner Opus

Interrogates the design, reconciles it with the repository, then writes the issues.

Holds decisions and trade-offs. Holds no implementation detail.
Executor Subagent

Takes one issue, writes the failing test first, implements, and reports back. Never commits.

Starts with a fresh context window and never sees the planning transcript.
Verifier Opus, again

Reads the diff against each acceptance criterion, runs the suite, commits, closes the issue.

Judges work it did not write, against a contract it wrote earlier.
What survives compaction
GitHub issuesthe contract

Test suitethe evidence

All of this runs on the Claude Code plan you already have. The models are swappable; the boundaries are the point.

Timing: 2 minutes.

The verifier and the planner are the same model in the same session, but they are doing genuinely different jobs at different times, against a contract written before the code existed.

Emphasize the fresh context window on the executor. That is the real delegation benefit: implementation detail, failed attempts, and test output never land in the orchestrator's window.

If someone asks about other vendors' models, say there is a slide at the end and keep moving.

Thinking before prompting05

Bring a position the planner can attack

Asking a model to invent the product from a blank page wastes the thing it is best at.

01Outcome and non-goalsWhat changes for the person using it, and what stays untouched?
02Domain and dataWhich concepts, rules, ownership, and lifecycles actually exist?
03UX statesWhat do empty, loading, success, error, and recovery look like?
04Failure behaviorRetries, partial work, invalid input, someone closing the tab.
05Codebase fitWhere should this live, and which existing boundaries matter?

Timing: 2 minutes.

This is your own thinking pass, before any prompt. The planner is far more useful when it receives a proposal with explicit trade-offs than when it receives a wish.

Do not polish the brief into false certainty. Mark what you feel strongly about and what you want challenged, so the grilling has somewhere to go.

For Caravan, this pass produced a one-page note: a roster from the directory, a roll call at every stop, activity polls, and one hard rule — the app never authorizes a departure, it only speeds up the leader’s check.

Planner role06

The grilling phase

Read my design and inspect the repository. Grill me one high-value question at a time. Focus on domain ambiguity, missing UX states, failure behavior, testability, and conflicts with the existing codebase. Do not implement anything or create issues yet.

Does a member check themselves in, or does the bus leader mark them?

What happens when someone swaps buses at a stop?

Does the app authorize the departure, or only report what the leader marked?

Who is the source of truth when the leader’s phone has no signal and a member’s does?

Output: resolved decisions, explicit unknowns, non-goals, and codebase constraints.

Timing: 3 minutes.

Stress the pacing. One question at a time. A list of twenty questions invites shallow answers and hides the moment when one answer invalidates an earlier decision.

These four are real questions from the Caravan session. The third one changed the product: it demoted the app from authority to advisory, which removed an entire class of liability and made the readiness rule something a pure function could own.

The planner must inspect the repository before it declares the design ready. An elegant plan can still be wrong for this codebase.

The durable handoff07

#7 — Departure readiness for a bus roll call

OutcomeThe bus leader gets one unambiguous answer — blocked or clear — and the name of every member still unaccounted for. Excused members never block a departure, and never disappear from the list.
ScopeOne pure readiness function and its unit tests. No interface, no storage, no sync, no notifications.
AcceptanceCovers an empty roster, a member with no mark at all, an excused member, a member reassigned to another bus mid-trip, and a leader mark overriding a stale self check-in.
EvidenceShow a failing test for the excused-member rule first, then the focused suite, then the full suite.
Non-goalsPush notifications, offline sync, location, polls, the photo feed, and anything that reads as the app granting permission to leave.
It survives compactionAn executor can start from this alone, with no planning transcript and no prior session.
Non-goals hold the lineWithout them the executor will helpfully build the awards too, and the sprint grows a day.
Evidence defines doneThe verifier gets something concrete to challenge instead of a claim to accept.

Timing: 3 minutes.

This is the interface between planner and executor. It states behavior, boundaries, and proof. It deliberately does not prescribe the implementation.

Read the acceptance list aloud. Every item there came out of the grilling phase, not out of my original brief.

Review every issue yourself before execution. This is the last cheap place to catch a wrong decision.

Timing: 3 minutes.

The subagent does not commit. That reserves the durable action for the orchestrator, and only after independent verification.

Test-first gives you a visible proof obligation. The red test should fail because the behavior is missing, not because the harness is broken. That distinction is worth saying out loud.

Sequential execution protects your ability to understand the branch. Parallel subagents are useful later, and only when the issues are genuinely independent.

Right-sizing the session09

Context is a sprint budget

HealthyRefresh soonRe-plan

Judgment degrades before output does. The orchestrator stops noticing problems well before it stops producing confident answers.

01Count dependencies, not issuesThree coupled issues can cost more context than six isolated slices.
02Watch verification residueFailed attempts and cross-cutting fixes stay with the orchestrator, not the subagent.
03Refresh after a small coherent batchRestart from issues, commits, and test output. Nothing important lives in the transcript.
04Stop when judgment gets expensiveRepeated regressions or moving issue boundaries are a planning problem, not a context problem.

45-minute detail

Use issue count as a ceiling, then lower it as coupling or verification cost rises.

Timing: 2 minutes on the 30-minute route, 4 on the 45.

There is no universal issue count. Pick a conservative ceiling, then watch how much branch state, failed approaches, and cross-issue reasoning the orchestrator has to keep holding.

My working heuristic: refresh after two or three non-trivial issues, or immediately after a verification failure that changes the plan. Starting point, not a benchmark.

Branch discipline10

Safety and recovery controls

main feature/caravan-rollcall

Stop on a design conflict, a destructive action, a repeated regression, or any change that crosses the active issue boundary.

Timing: 1 minute on the 30-minute route, 3 on the 45.

Work on a branch cut from main. Keep it clean before orchestration starts, and make each commit correspond to exactly one closed issue. That gives you a recoverable checkpoint before the next executor begins.

Focused tests first for fast feedback, full suite before committing. If the full suite fails, the issue stays open. No exceptions, because the exception is how the discipline dies.

Write your stop conditions before the run, not during it.

The demo, part two12

One brief, cut into issues

Ordered by dependency, and by what actually earns the install. Each slice is independently shippable and independently testable.

The fun part was built last on purpose.

01Roster and itineraryDirectory sync, bus assignment, stops. Almost no open decisions, so it went first.
02Roll callReadiness, excused members, reassignment. The real design work, and the slice we are about to read.
03Activity pollsQuorum, ties, changing your vote, what closes a poll. Contested rules, clean slice.
04Call timesAn acknowledgement board first. Push was specified as an enhancement, never a dependency.
05Photos, gallery, awardsLast, deliberately. By then everyone already had the app for reasons they could not skip.

Timing: 2 minutes on the 30-minute route, 3 on the 45.

This slide is the decomposition itself, and it is worth naming as a skill. The hard part of the workflow is not the prompting; it is cutting a brief into slices that can be finished, tested, and closed one at a time.

Say why the photo feed is last. A feature nobody has to open cannot carry adoption. Roll call and call times are mandatory, so they put the app on every phone, and the gallery gets used for free afterwards.

If someone asks why not build the fun thing first: it was the original plan, and it was wrong for exactly that reason. Being straightforward about the reversal is worth more than pretending the first plan was right.

Timing: 3 minutes.

Keep the claims personal and specific. Say “in my projects” rather than stating anything as a general property of the models.

Context headroom is the honest version of the benefit. Subagents get their own windows; that is real and it is measurable in how long a session stays coherent.

Give the cost column equal airtime. The room will trust the gains more if you are visibly unsentimental about the costs.

Proportional process16

When this is worth it

Worth the orchestration

Run the full workflow

The requirement still has unresolved product or domain decisions in it.

The change crosses interface, data, and business rules.

Tests can define a finish line you would actually believe.

The work splits into independent vertical slices.

Use something lighter

Skip the handoff

A small, obvious patch costs less than the handoff does.

An urgent hotfix needs your own hands on it.

The repository has no test harness you would trust.

It is an exploratory spike with no stable definition of done.

The method earns its cost when ambiguity and verification risk exceed the orchestration overhead.

Timing: 2 minutes.

Say explicitly that a typo fix does not need a planner, an issue, an executor, and a verifier. Turning this into ceremony is the fastest way for a team to abandon it.

The sweet spot is a feature with real design work in it, a testable outcome, and slices that can be done one after another without integration chaos.

45-minute detail

Useful extensions: hooks for deterministic safety or test gates, and browser tools when an issue needs interface or console evidence. Load browser tools on demand — they cost context.
